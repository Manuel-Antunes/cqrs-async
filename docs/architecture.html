Architecture

The two sides and what connects them​

                 WRITE SIDE                                       READ SIDE
 ┌─────────────────────────────────────────────┐   ┌─────────────────────────────────────┐
 │ PostCommandGateway (is the handler)          │   │ PostQueryGateway (is the handler)   │
 │   impl CommandHandler<PublishPost>           │   │   impl QueryHandler<FindPost>       │
 │      find │ decide │ ctx.record │ save       │   │                 │ read              │
 │           ▼        ▼            ▼            │   │                 ▼                   │
 │   PostRepository (your port, your Tx)        │   │   PostSummaryRepository (your port) │
 │                                              │   │                 ▲ write             │
 │   unit of work (#[gateway(unit)]):           │   │   PostProjection                    │
 │   begin → handle → append → commit           │   │     namespace "summaries"           │
 │                     │                        │   │     namespace "notifications"       │
 │                     ▼                        │   │                 ▲                   │
 │               EventStore  ════════════════════════► TrackingProcessor per namespace   │
 │        (source of truth, global order)       │   │   unit of work: handle + token      │
 └─────────────────────────────────────────────┘   └─────────────────────────────────────┘
                       │                                               │ handled
                       ▼                                               ▼
              EventFeed (a Stream)                       QueryUpdateEmitter<Self>
          catch-up subscriptions                  subscription queries (live results)
  • Write side. A command goes through a gateway to exactly one handler. The handler finds entities through the application's own repository, lets the domain decide (append events), and records them for the entity they change. The framework's unit of work appends what was recorded, with optimistic concurrency, and commits.
  • The event store is the only source of truth. Every event gets a stream (post-42), a sequence within it, and a global position.
  • Read side. A projection, one per aggregate root, turns committed events into read models and side effects, one namespace each. Queries read the read models, never the store.
  • What connects them is event processing: inline, right after each commit, in the caller's task; or by tracking processors that follow the store on their own tasks, each event in a unit of work that commits the handler's changes with the processor's token.

A command, end to end​

The blog's PublishPost, on PostgreSQL. The handler is an impl on the gateway, in the use case's file:

// src/application/commands/publish_post.rs
#[cqrs::command_handler]
impl<R: PostRepository, P> CommandHandler<PublishPost> for PostCommandGateway<R, P> {
    async fn handle(
        &self,
        command: &PublishPost,
        ctx: &mut CommandContext<PostEvent>,
        tx: &mut R::Tx,
    ) -> Result<(), BlogError> {
        let post = self.posts.find(command.id, tx).await?.ok_or(NotFound(command.id))?;
        post.publish(ctx)?;
        let post = ctx.record(post);
        self.posts.save(&post, tx).await?;
        Ok(())
    }
}
  1. Dispatch. app.commands().send(PublishPost { id }). The gateway (#[cqrs::command_gateway(commands = PostCommands, handles(CreatePost, RetitlePost, PublishPost))]) routes it to its CommandHandler<PublishPost> impl, chosen at compile time. Interceptors added with .intercept(..) wrap the gateway.
  2. The unit of work opens. The gateway runs the command in a unit of work of its #[gateway(unit)] field (the unit's Events). Because handle takes tx: &mut R::Tx, the mode is InTransaction<Tx>: the unit begins a transaction and lends it. Without a tx argument the mode is Autocommit: no transaction, one entity per command.
  3. The handler decides. It finds the post in its repository (Loaded<Post>: the state and the version it was read at), lets the domain append through ctx (an EventAppender<PostEvent>), and calls ctx.record(post). Recording assigns the appended events to that post and returns it evolved, at its new version; nothing is written yet. The repository saves that state in the same transaction (the SeaORM adapter does; the event-sourced one has Tx = () and saves nothing more).
  4. The unit appends and commits. Once handle returns Ok, the unit appends what was recorded, in the transaction, expecting the version the post was loaded at, and commits: the post's row and its events commit together, or not at all. The handler never commits.
  5. A lost race reruns the handler. If the stream moved on (or a DCB condition failed), the transaction is rolled back and the handler runs again on fresh state, up to conflict_retries (8 by default). That is why a handler has no side effects besides what it writes in tx: an e-mail belongs in a projection namespace, after the commit.
  6. The commit is announced. Events broadcasts the committed envelopes on its live feed, which wakes the tracking processors; an InlinePublisher runs its handlers right away instead. send returns the command's output.

From events to projections​

A projection is one struct per aggregate root, holding what its handlers need, with one EventHandler impl per namespace:

// src/application/projections/post/mod.rs
#[cqrs::projection(
    name = "post",
    events = PostEvent,
    namespaces("summaries", "notifications"),
    updates(FindPost, ListPublished),
    subscriptions = PostSubscriptions
)]
pub struct PostProjection<S, N> {
    /// Where the summaries are kept.
    summaries: Arc<S>,
    /// Who delivers the announcements.
    notifier: Arc<N>,
}
  • Namespaces. Each namespace (#[cqrs::event_handler(namespace = "summaries")]) is run by a tracking processor of its own, named "{projection}.{namespace}" (post.summaries, post.notifications), with its own tokens. A failing notification never holds the read model back. The namespace lives on the projection, not on the event: the domain does not know who consumes it.
  • Tracking processors. A processor reads the log in global order and splits it into segments by stream, so a post's events stay in order and different posts run in parallel (TrackingOptions::segments). Segments are claimed in the TokenStore, so several instances share the work and take over a dead instance's segments.
  • Tokens. A segment's token is a Cursor: the highest position seen, plus the gaps a parallel append left behind. For each event (or batch, with batch = N) the processor opens a unit of work with its TransactionManager, runs the handler and its interceptors, stores the token, and commits. A read model in the same database as the tokens applies each event exactly once; a side effect outside it is at-least-once.
  • Failures. A failing event is rolled back and retried with backoff, holding back only its own segment. With a DeadLetterQueue, after a number of attempts it is parked with the later events of its stream, and everything else keeps flowing.
  • Replay. reset calls each handler's reset (clear the read model) and rewinds the tokens. Namespaces with const REPLAY: bool = false (notifications) skip the replayed events.

Inline or asynchronous. The same projection runs either way:

  • Cqrs::from_publisher(InlinePublisher::new(store).with_projection(p)): each namespace sees each commit right after it, in the caller's task, isolated from the others. No runtime, deterministic: what domain and flow tests use. A failing handler does not undo the commit; the failure goes to the publisher's on_failure (LogFailures, logging at error level, by default).
  • Cqrs::new(Events::new(store)).projection(p): commands return once committed, and each namespace follows on its own processor. Read models are eventually consistent; app.settled().await waits for them, and several units together are a tuple ((posts, users).settled().await).

On PostgreSQL only the events change: cqrs_postgres::Postgres::new(pool).events::<PostEvent>("posts") gives the same Events with the database's tokens and transactions. Each aggregate root has its own log; all logs share one global position sequence.

Subscription queries​

A subscription query is the current result of a query, then every update of it. The projection lists its queries in updates(..) and gets one channel per query, QueryUpdateEmitter<Self>. A namespace emits in its updated step:

// src/application/projections/post/summaries.rs
async fn updated(&self, event: &EventEnvelope<PostEvent>, updates: &QueryUpdateEmitter<Self>) {
    let Ok(id) = post_of(event) else { return };
    if let Ok(Some(summary)) = self.summaries.find(id).await {
        updates.emit(|query: &FindPost| query.id == id, Some(summary));
    }
    if matches!(event.payload, PostEvent::Published)
        && let Ok(published) = self.summaries.published().await
    {
        updates.emit(|_: &ListPublished| true, published);
    }
}

updated runs on every instance, once that namespace handled the event, whichever instance handled it: every subscriber gets the update, wherever it is connected, and never sees a change that was rolled back. Emitting for a query not listed in updates(..) does not compile.

A client calls app.queries().subscribe(FindPost { id }): the current result, once the read-model namespaces handled what was committed when the subscription started (so a client sees its own commands), then the updates. subscriptions = PostSubscriptions names the trait the API depends on.

Layers in an application​

The blog uses four layers, with dependencies pointing inwards:

presentation ──► application ──► domain
      │               ▲
      └─► (ports) ◄── infrastructure        composition root (config.rs) wires them
LayerContainsKnows the library as
domainAggregates, events, domain errors#[cqrs::aggregate], EventAppender, #[derive(cqrs::DomainEvent)]
applicationCommands and the command gateway; queries and the query gateway; the projection and its namespaces; repository ports (write and read side)CommandHandler, CommandContext, Loaded, QueryHandler, EventHandler, QueryUpdateEmitter
infrastructureAdapters: the posts' repositories (event-sourced, SeaORM), the read model, the notifier, interceptorsThe port traits it implements, AggregateLoader, Interceptor, EventInterceptor
presentationGraphQL over axum, written against the generated traitsPostCommands, PostQueries, PostSubscriptions, EventFeed
composition root (config.rs)The stores, the adapters, the Cqrs unitCqrs::new, Cqrs::from_publisher, the stores

Projections live in the application layer: what a read model holds is application logic, and where it is stored is a port.

Where the shapes differ, the reason is almost always the same: Axon discovers handlers by reflection and keeps them in registries; here the type system has to see every handler, so they are trait impls on a gateway or a projection, listed in its attribute, and the compiler does the routing.
