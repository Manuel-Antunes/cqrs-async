CQRS and event sourcing for Rust, resolved at compile time.

A library, not a framework. Commands and queries are routed to their handlers by the compiler, projections commit with their position in one transaction, and everything is async from the ground up. Bring your own database, ORM and runtime.

retitle_post.rs
#[cqrs::command(error = BlogError)]
#[derive(Debug, Serialize, Deserialize)]
pub struct RetitlePost {
    pub id: PostId,
    pub title: String,
}

#[cqrs::command_handler]
impl<R: PostRepository, P> CommandHandler<RetitlePost> for PostCommandGateway<R, P> {
    async fn handle(
        &self,
        command: &RetitlePost,
        ctx: &mut CommandContext<PostEvent>,
        tx: &mut R::Tx,
    ) -> Result<(), BlogError> {
        let post = self.posts.find(command.id, tx).await?.ok_or(NotFound(command.id))?;
        post.retitle(command.title.as_str(), ctx)?;
        let post = ctx.record(post);       // the post after its events
        self.posts.save(&post, tx).await?; // same transaction: the framework commits
        Ok(())
    }
}

One impl per command. Find, decide, record: the library commits.

Checked by the compiler

No handler registry behind dyn, no Any, no TypeId. A missing or duplicated handler is a compile error, and the running code is plain function calls.

Your infrastructure

The core depends on no database, ORM or broker. Connections and transactions are yours; the library borrows them. Adapters adapt to your system, never the reverse.

Async, all the way

Every contract is a Future or a Stream. Committed events are a stream you can hand to axum, async-graphql or a Tokio task.

What you get

Small pieces that fit together, each one usable on its own.

Messages & gateways

Commands and queries are plain structs that own their output and error types. A gateway struct implements a handler per message it lists in handles(..).

Plain aggregates

Decisions take &self and an appender; state changes only in apply. The domain barely knows the library.

Consistency

Optimistic concurrency per stream, plus dynamic consistency boundaries: tags, criteria and conditional appends.

Event processing

One projection per aggregate, one processor per namespace: read models replay, side effects do not. Inline or on tracking processors with segments, tokens and batches.

Unit of work

The library commits: a command's state and events in one transaction, a projection's read model with its position in another. Nothing is lost or applied twice.

Live queries

A projection lists its subscription queries and emits their new results; subscribers see their own writes, on every instance.

Interceptors

Around gateways and around event handlers, inside their transaction. A chain compiles to nested calls.

Storage

In memory, and PostgreSQL over sqlx with compile-checked SQL, parallel appends and a gap-aware cursor.

Testing

A given/when/then fixture for aggregates and a tiny block_on: everything runs without an async runtime.

Events are facts. Aggregates are plain structs.

A decision reads &self and appends events; it cannot assign state, so that does not compile. evolve is the only place state changes, when an event is recorded and when it is replayed.

Part 1: the domain →

#[derive(Clone, Debug, PartialEq, Serialize, Deserialize, cqrs::DomainEvent)]
pub enum PostEvent {
    #[event(name = "post.created")]
    Created { id: PostId, title: String },
    #[event(name = "post.retitled")]
    Retitled { title: String },
    #[event(name = "post.published")]
    Published,
}

#[cqrs::aggregate(name = "post", event = PostEvent)]
#[derive(Clone, Debug, PartialEq, Serialize, Deserialize)]
pub struct Post { id: PostId, title: String, published: bool }

impl Post {
    pub fn publish(&self, events: &mut impl EventAppender<PostEvent>)
        -> Result<(), PostError>
    {
        if self.published {
            return Err(PostError::AlreadyPublished);
        }
        events.append(PostEvent::Published);
        Ok(())
    }
}
